# 项目统一走读入口

**简体中文** | [English](final_walkthrough.en.md)

## 当前范围

本文只讲原两寄存器 APB3 教学基线。项目现在另有 APB+UART 扩展，规格和运行入口见 [项目 README](../README.md)；两者都不是完整 UVM 验证 IP。

## 按一笔请求串起来

1. 规格：地址 00 可读写、04 只读，等待时不提前更新。
2. `submit` 保存原始计划，`drive` 发出信号。
3. 协议检查器逐拍检查准备、等待和完成转换。
4. 监视器仅在完成沿记录请求与响应。
5. 请求匹配检查是否真的执行了计划内容。
6. 记分板按规格检查错误响应、更新期望或比较读数据。
7. 通过检查的完成记录进入功能覆盖计数。
8. 收尾检查未完成请求、计数及覆盖门槛。

从 `submit(1, 0, 32'h2a)` 和随后的读取开始，不需要一口气读完所有脚本。

## 审计后的改进

- 随机补齐末尾写入全一后增加读回，再复位；当前随机每组 219 笔，早期 218 笔报告是历史记录。
- 原基础脚本增加编译进度提示和编译失败日志，避免运行时长时间看似没动。
- 电路层补足五类人为故障，分别验证时机、错误响应、只读保护、复位及读数据。

## 必须诚实说明的限制

- 功能覆盖 11/11 只针对已定义的 11 格，不是全部协议或代码覆盖率。
- 三个等待参数固定测试，未实现每笔随机延迟或任意参数证明。
- 基础测试覆盖中途复位；分层请求队列目前只在请求之间复位，尚无中途取消机制。
- 协议检查使用即时断言和历史采样值，没有并发 property。
- Verilator 回归不能作为四态 X/Z 行为全面验证的证据，即使用了严格比较运算符。
- 随机写入若随后被覆盖且未读回，不能仅凭本模型证明每次内部存储都正确。基础白盒定向检查与尾部读回补充检查，不是形式证明。
- 五种电路故障、驱动故障和观察值污染都是人为教学案例。

## 复现与调试

运行 `make regression`；沿写 2A 再读取的流程检查各角色。负向运行应在对应错误标记处停止，再使用关闭注入的正常配置复测。最新结果见 [发布回归](../reports/publication_regression.md)。
