# 请求有没有按计划执行

**简体中文** | [English](request_matching.en.md)

## 数据流

```text
submit 保存原始计划到 pending 队列
    ↓
drive 把请求变成信号
    ↓
monitor 在完成沿记录实际请求和响应
    ↓
match_request 对照 pending 中最早的一笔
    ↓
score 检查响应、更新期望值
```

计划队列与电路内部数据、监视记录都独立。先保存计划再驱动，不能把驱动出错后的信号作为计划。

## 三种基本判断

- 有计划、有完成：比较地址、方向、写数据；读操作不比较写数据。
- 没有计划、有完成：出现额外传输，报 `REQUEST_UNEXPECTED`。
- 测试结束仍有计划没完成：出现遗漏，报 `REQUEST_MISSING`。

`planned` 是登记的请求数；`matched` 是匹配成功数；`received` 是通过功能检查的观察数。正常结束要求三者都是 9，并且队列为空。仅比较总数不够，因为发错地址也可能保持总数不变。

## 五个人为错误

| 故障 | 实际动作 | 预期错误 |
|---|---|---|
| address | 第一笔计划写 00，却发送写 04 | REQUEST_ADDR |
| direction | 第一笔计划写，却发送读 | REQUEST_DIR |
| data | 第一笔计划写 2A，却发送 2B | REQUEST_DATA |
| drop | 登记最后一笔，但不发送 | REQUEST_MISSING |
| duplicate | 最后一笔完成后，没有新计划却重发一次 | REQUEST_UNEXPECTED |

五项都保持原计划不变，分别在等待 0、1、3 下测试。它们是驱动路径的教学故障，不是实际 DUT 缺陷。成功报错说明请求检查有效；不能宣称已经证明调度器绝不会遗漏生成计划。

## 复位与边界

本版在计划完成之后才复位，复位前检查队列已空。复位不清除计划计数，也不偷偷丢弃队列内容。中途复位如何把请求标成取消，留待后续扩展。

计划按顺序匹配，适合当前非流水、单发起方 APB。暂未添加独立乱序故障用例。相同内容的请求没有总线事务 ID；仅凭信号无法区分两个完全相同请求的内部身份。

## 阅读入口

先看 `request_t` 和 `pending[$]`，再看 `submit`、`match_request`，最后看主测试结尾的队列及计数检查。原来的基础 20 笔测试没有改。
