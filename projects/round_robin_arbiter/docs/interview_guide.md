# Round-robin Arbiter 面试讲法

## 30 秒回答

我实现了一个四请求者 round-robin arbiter（轮询仲裁器），用于解决多个请求者争用同一个共享资源时的公平分配问题。模块从 `priority_ptr` 指定的位置开始循环搜索，跳过没有请求的人，并只授权第一个有效请求者。组合逻辑根据当前请求和轮询起点生成独热授权与下一指针，时序逻辑在时钟上升沿保存下一指针。相比固定优先级仲裁，持续请求者可以在最多四次授权机会内得到服务，避免长期饥饿。

## 1 分钟回答

我实现的是四请求者 round-robin arbiter（轮询仲裁器）。它解决多个请求者同时访问一个共享资源时由谁先使用的问题。设计内部保存两位 `priority_ptr`，它表示本轮从哪个请求者开始搜索；找到第一个有效请求后生成 one-hot（独热）`grant`，并把 `priority_ptr_next` 移动到获授权者的后一位。没有请求时，授权保持全零且指针不移动。

实现上，组合逻辑读取 `req` 和当前指针，计算 `grant` 与下一指针；时序逻辑使用低电平有效异步复位，并在时钟上升沿保存下一指针。验证平台不读取内部状态，而是使用独立参考模型完成 64/64 个状态与请求组合穷举，并用 64 次全请求探针从接口确认下一状态；另外覆盖 60/60 个持续请求公平性场景、四条 SVA 和 1,712 次自动比较。我还自动注入错误回卷故障，确认黑盒记分板能够检出状态更新错误。

## 面试官追问

### 1. 为什么需要状态

如果没有状态，每个周期都从固定请求者开始搜索，就会退化成固定优先级仲裁器。`priority_ptr` 用来记住本轮搜索起点，使下一轮能够从获授权者的后一位继续。

### 2. 没有请求时为什么不移动指针

没有实际服务任何请求者时，移动指针没有公平性依据，还会改变下一次请求到来时的优先顺序。基础版本因此保持原指针。

### 3. 如何检查授权合法

检查 `(grant & ~req) == 0`，可以保证模块不会授权没有发出请求的人。检查 `grant == 0` 或 `(grant & (grant - 1)) == 0`，可以保证授权为全零或独热编码。

### 4. 如何说明公平性

在基础版本假设每次非零授权都完成服务的条件下，如果某个请求持续保持有效，搜索起点会在四个请求者之间循环，因此该请求者最多等待四次授权机会。

### 5. 如果资源拒绝本次授权怎么办

当前基础版本假设每个非零 `grant` 都代表服务成功。真实系统如果存在接受或就绪信号，只有在“授权有效且资源接受”的握手完成时才应更新指针，否则应该保持当前指针。

### 6. 请求者数量增加后有什么问题

当前四请求者版本使用明确的 `case` 分支，便于学习和检查。请求者数量增加时，重复逻辑和组合搜索路径都会变长，需要改为参数化实现，并评估组合逻辑的时序路径。

## 常见错误回答

- “它每次直接选择下一个编号。”错误原因：下一个编号可能没有请求，仲裁器需要循环搜索并跳过无请求者。
- “组合逻辑负责全部功能。”错误原因：公平轮询依赖历史状态，必须由时序逻辑保存轮询起点。
- “所有人一定严格按 0、1、2、3 获得授权。”错误原因：只有持续请求时才表现为严格轮转，未请求者会被跳过。
- “仿真通过就证明没有任何错误。”错误原因：仿真只能证明已覆盖场景中的检查通过，还需要关注遗漏场景、断言、覆盖率和实现时序。

## 更专业的回答

这是一个四端口公平仲裁模块。组合路径根据当前请求向量和轮询起点执行带回卷的优先搜索，输出全零或独热授权，同时计算下一轮起点；状态路径只在复位或时钟上升沿更新轮询指针。基础接口假设授权即服务完成，因此每个非零授权都会推进指针。验证方面，我使用与 DUT 不同实现方式的独立参考模型，穷举全部 64 个合法状态与输入组合，并通过黑盒探针检查状态推进；持续请求公平性、接口断言和错误回卷故障注入也进入自动回归。若接入真实共享资源，我会增加接受握手，并只在事务真正完成时推进指针。

## 缩写与术语

- DUT = Design Under Test，被测设计。
- testbench = 测试平台 / 测试代码。
- round-robin = 轮询调度。
- arbiter = 仲裁器。
- one-hot = 独热编码，多个位中最多只有一位有效。
